# Assurance OS (GRC): module build standards

Every remaining module prompt references this document. Each module is held to
it before merge. These standards encode what the build has already established,
so no module reintroduces a solved problem. Where a standard names a file, that
file is the single place to change if the live system ever differs.

## Non-negotiables (apply to every module)

### 1. Typed columns

All queries go through the typed column layer generated from the live schema
(build prompt 18): `src/lib/grc/schema/columns.ts`, generated by
`grc/db/gen-columns.mjs` from the ground-truth dictionary `grc/db/schema.md`
(the in-repo copy of `grc-data-dictionary.md`). No hand-written column strings
in SQL or in code. Take every column name via `cols()` or `C.<table>.<column>`
so a wrong or non-existent name is a compile error and fails `pnpm build`, not
the user's screen. If the dictionary is wrong, fix `grc/db/schema.md`,
regenerate with `node grc/db/gen-columns.mjs`, and commit both files.

### 2. Verification harness

Build prompt 22 establishes the harness; every module after it stays green
behind it:

- Every route has an error boundary. A query or render error becomes a logged,
  branded error card in the page, never a blank 500.
- Every new page and every mutation is added to the smoke test in `grc/test/`
  and must pass it before merge.

### 3. CRUD round-trips

Anything editable in the UI persists to the database: create inserts, edit
updates, delete soft-deletes via `deleted_at` or `is_active` where the table
has them. Every mutation shows a saved or error state in the UI. Destructive
actions confirm before acting.

### 4. Affordances

Interactive elements signal themselves: pointer cursor, hover state, edit and
delete icons, chevrons for drill-through, drag handles where reorderable.

### 5. States

Every screen has proper empty, loading and error states. A list with no rows
shows a clean empty state, never an error.

### 6. Tenancy and permissions

Every read and write is scoped by the acting `organization_id` (resolved via
`src/lib/grc/auth/actingOrg.ts`). A SUPER_ADMIN may edit anything within their
organisation; the platform owner (`users.is_platform_owner = 1`) may act across
organisations by entering an instance, and is inside none of them until they do
(`grc/docs/tenancy.md`). A new page or endpoint that reads or writes an
organisation's data needs an instance: leave it out of `INSTANCE_FREE_PATHS` in
`src/lib/grc/routing.ts` and the middleware prompts an owner with none selected
to pick one. Gate actions with `can(locals, action, module)`
from `src/lib/grc/auth/rbac.ts` against the seeded `role_permissions` matrix;
the gate applies the source aliases (`view` to `read`, `WORK_PAPERS` to
`WORK_PAPER`). Never gate by hard-coded role checks when the matrix can answer.

### 7. Data-driven workflow

Statuses and transitions come from the database: `enum_values`,
`status_transitions` (with `required_role` and `requires_comment`) and
`workflow_terminal_states`, read through `src/lib/grc/workflow/`. Never
hard-code a status list or an allowed transition.

### 8. House style

- British and Kenyan spelling; no em dashes.
- Strict TypeScript with no bare `any`.
- WCAG 2.2 AA.
- The Murikah navy/gold/paper design system.
- No secrets in the repo (runtime secrets go in `.dev.vars`, gitignored; see
  `grc/docs/deploy.md`).
- Do not touch Engineering Rhythm (`src/lib/engr`, `src/components/engr`,
  `src/pages/engr`, `engr/**`).
- Each module is its own pull request previewing on Cloudflare, and passes
  `pnpm lint`, `pnpm build`, `pnpm test` and `pnpm format:check`.

## Repository layout (where GRC code actually lives)

The GRC product mirrors Engineering Rhythm's layout in the `wmurikah/Murikah`
monorepo. Put code in these locations, not in a single top-level `grc/` folder:

- `src/lib/grc/**`: application logic. `schema` (the typed columns), `auth`,
  `repos` (data access), `workflow`, `notify`, `storage`, `reports`,
  `dashboard`, `ai`.
- `src/components/grc/**`: UI components (islands and partials).
- `src/pages/grc/**`: routes and API endpoints (pages under `src/pages/grc/...`
  and endpoints under `src/pages/grc/api/...`).
- `grc/test/**`: tests, including the smoke test.
- `grc/db/**`: schema and generated column artefacts (`schema.md`,
  `gen-columns.mjs`).
- `grc/docs/**`: module docs (`completion.md`, `schema-assumptions.md`, etc.).

This mirrors `src/lib/engr`, `src/components/engr`, `src/pages/engr`,
`engr/test`, `engr/db`. Follow it exactly so new code lands where the existing
GRC code already is.
